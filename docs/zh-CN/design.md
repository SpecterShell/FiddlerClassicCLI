# CLI 与 MCP 设计

[English (en-US)](../en-US/design.md) | **简体中文 (zh-CN)**

此集成采用 [Chrome DevTools MCP](https://github.com/ChromeDevTools/chrome-devtools-mcp) 面向代理的原则和列表/详情工具模式，并保留 Fiddler Classic 的术语和进程级抓包模型。

## 功能分类

功能按行为来源分为原生、原生适配、自定义、混合或主程序功能。[功能类型与原生兼容性矩阵](feature-types.md)定义了各项 CLI 和 MCP 功能的一致性约定。自定义查询、等待、比较和传输操作各有独立规范，不声称复现名称相近的 Fiddler UI 标签页。

## 发布与安装

已发布的 Windows x64 主程序是自包含单文件程序，嵌入了 .NET 运行时、托管依赖、桥接和协议 DLL 及 `LICENSE`。`bridge install` 命令负责部署嵌入的 DLL。程序运行时，.NET 默认将原生运行库文件提取到 `%TEMP%\.net`。发布输出目录和 Release 目录各自仅包含此 EXE，GitHub Release 也仅上传该文件。文档和 Agent Skills 保留在源码仓库中，CI 通过元数据在任务之间传递可执行文件和嵌入桥接的哈希。

`scripts/install.ps1` 默认从 `SpecterShell/FiddlerClassicCLI` 的最新发布版本下载名称完全一致的 `fiddler-classic-cli.exe`。脚本要求 GitHub 提供文件 SHA-256 摘要，并在执行前验证下载内容。显式指定 `-PackagePath` 可选择可信的本地可执行文件或目录，也可选择 ZIP，但要求相邻的 `SHA256SUMS` 中有与其文件名完全一致的校验条目。脚本默认使用固定目录 `%LOCALAPPDATA%\Programs\FiddlerClassicCLI`，更新当前用户的 PATH 并部署桥接，可通过参数跳过相应步骤。它不会启动 Fiddler、守护进程或 MCP 服务器，也不配置 Agent Skills。选项和输出说明见[安装指南](installation.md)。

## 检查工作流

官方 C# SDK 2.2.0 负责 MCP 序列化和传输生命周期。协议版本 `2026-07-28` 使用逐请求元数据，并可通过 `server/discover` 查询服务信息。旧版客户端使用初始化握手。前台和守护进程托管的 HTTP 监听器均采用 `HttpServerSessionMode.Stateless`。桥接协议版本 3 和守护进程协议版本 1 独立于 MCP 协议版本。

协议测试通过两种传输发送原始 JSON-RPC，验证服务发现、工具 schema 和安全注解、版本错误，以及限长结构化结果。SDK 客户端测试分别固定使用 `2026-07-28`、`2025-11-25` 和 `2025-06-18`，防止自动回退掩盖回归问题。HTTP 测试还验证标头与正文的一致性，并确认取消请求能传递到待完成的桥接通信。本项目不声明可选的 Tasks、Apps 或服务端主动请求客户端交互的能力。

选择能回答当前问题且范围最小的工具：

1. 调用 `list_network_requests` 过滤摘要并取得请求 ID。
2. 调用 `get_network_request` 获取一个事务。标头需要显式请求，只有 `includeHeaders=true` 时才返回。
3. 仅在需要载荷字节时调用 `get_network_request_body`。每次最多读取 64 KiB，并以 `offset + bytesReturned` 继续，直至 `eof=true`。
4. 调用 `wait_for_network_request` 获取下一个已完成的匹配请求，无需轮询完整列表。

CLI 通过 `sessions list`、`sessions show` 和 `sessions body` 提供相同的逐步检查流程。默认输出为可读文本，`--json` 为脚本提供稳定的结构化数据。CLI 将完整正文写入显式指定的文件或 stdout，不会将其嵌入元数据结果。

单独运行可执行文件或命令组时，CLI 将相应帮助写入 stdout，退出码为 0，与 `--help` 相同。缺少必需输入或发生其他解析错误时，CLI 将命令帮助和错误写入 stderr，退出码为 2，不执行操作。使用 `--json` 时，stderr 仅包含结构化错误。解析错误不会向 stdout 写入内容，避免污染载荷流。

依赖桥接的 CLI 命令使用自动启动的后台守护进程。每次调用通过仅限当前用户访问的 Windows 命名管道发送一个已封帧的请求，守护进程再通过现有的带版本桥接协议将请求转发给 Fiddler。抓包状态由 Fiddler 持有，守护进程不持有该状态。

守护进程还管理可选的持久 MCP HTTP 监听器。Fiddler 扩展通过同一个当前用户控制管道访问它。前台 `mcp http` 与守护进程监听器共用同一套 Kestrel 主程序实现。Fiddler 标签页在 UI 线程之外执行控制和进程操作，每两秒刷新一次，请求不会重叠，只有控件更新会切换回 Fiddler UI 线程。扩展卸载时会移除标签页和菜单项，守护进程与监听器继续运行。

每次标签页控制通信都有十秒的时限，覆盖连接、请求写入和响应读取。取消操作会关闭管道，中断挂起的 .NET Framework I/O。启动发现过程另有十秒的时限。守护进程拒绝 `stop` 消息封装时不会退出。表格刷新通过稳定 ID 恢复选中项和滚动位置。原选中项已移除时，选择保持为空。服务禁用时，刷新会保留尚未应用的设置。

`bridge install` 会在 Fiddler Scripts 目录之外写入当前用户启动记录。该记录指定扩展可以启动的确切主程序和版本。守护进程状态通过附加的 `managed-http-v1` 能力报告对托管 HTTP 的支持。新版扩展可据此提示用户重启旧版守护进程，无需更改守护进程协议版本 1 或现有管道名称。

扩展的启动任务独立运行，不依赖标签页的创建或选择。卸载会取消该任务，守护进程继续运行。每次标签页刷新都会在 UI 线程之外读取启动记录和守护进程状态，以显示当前版本。

只读 Named pipes 区域结合本地桥接监听器快照与现有的守护进程状态响应，显示完整管道路径、支持的协议版本、当前用户 ACL 访问范围，以及守护进程 PID 和 UTC 启动时间。桥接生命周期状态和最近一次监听器错误来自桥接服务器。守护进程状态检查失败时，进程详情会清除为 `Unknown`，界面报告检查失败，不据此判定守护进程已停止。该区域不显示凭据或流量，也不跟踪管道连接。

管道状态沿用标签页每两秒一次且不重叠的刷新。独立的 **Refresh pipes** 操作仅读取桥接快照和守护进程状态，不调用启动或监听器配置操作。守护进程仍由扩展初始化过程启动。状态显示使用现有的桥接 v3 和守护进程 v1 协议。

发现过程仅在连接建立前超时且成功取得现有守护进程所有权管道时，才报告守护进程已停止。离线管理在整个读取或配置事务期间持有该所有权，防止守护进程并发启动。连接建立后的超时、状态请求被拒绝和响应格式错误均作为错误传递。关闭操作收到停止确认后，会等待所有权释放。

HTTP 服务默认禁用并绑定回环地址。保存的配置包含启用状态、绑定模式、端口、为兼容而保留的可显示默认令牌，以及命名客户端记录。命名令牌由 256 位随机数据生成，只显示一次，配置中只保存其 SHA-256 哈希。身份验证层以固定时间比较哈希，并在配置文件被原子替换后重新加载凭据。

当前用户的命名互斥锁在进程和 Windows 会话之间保护每次完整的配置读取、修改和写入事务。锁名称由规范化的配置路径生成，获取锁最多等待五秒。写入使用原子替换和当前用户 ACL。如果进程持有锁时退出，下一个持有者会重新加载最后一份完整的配置文件。

凭据快照在同一个互斥锁内读取令牌哈希和配置文件时间戳。并发轮换不会将较新的时间戳关联到旧凭据。前台和托管监听器使用相同的逻辑重新加载默认及命名凭据。守护进程的连接控制仅适用于自身的监听器。已分派的前台请求在撤销凭据后仍可能继续执行。

Kestrel 连接中间件只记录连接 ID、远程端点、授权和客户端状态、连接及活动时间，以及活动和累计请求数。它不会保留 URL、标头、令牌、正文或抓包流量。断开操作会中止一个传输连接。撤销凭据会中止与其关联的全部活动连接。已分派的操作可能已经完成。

已完成会话的通知会写入进程内的限长 ID 缓冲区。等待操作在 Fiddler UI 线程之外休眠，只在获取匹配快照时切换回 UI 线程。请求构造和重放会返回基准会话 ID、预期方法与 URL。可选等待功能使用这些值查找首个匹配的已完成会话。

## 抓包挂接

`capture start` 和 `capture stop` 调用 Fiddler 原生操作，将其挂接为运行它的 Windows 主机的系统代理或取消挂接。两者保留证书信任和 HTTPS 解密设置。取消挂接后，运行中的 Fiddler 代理监听器仍可通过回环地址或已配置远程访问的可达接口接收显式路由的流量。IPv4 `0.0.0.0` 表示绑定所有 IPv4 接口，客户端连接具体的主机地址和代理端口，并须满足路由和防火墙规则的要求。MCP HTTP 绑定控制独立的监听器，不会配置 Fiddler 代理访问。

## Fiddler 应用程序管理

诊断、桥接安装和 CLI 专有的 `app` 命令共用 `FiddlerEnvironment` 的只读安装检测。`FiddlerAppService` 通过小型 Windows 进程接口协调目标选择、确认和有时限的退出等待。测试使用模拟进程句柄，不启动或关闭用户的 Fiddler 实例。

Windows 实现会在选择目标前验证进程所有者 SID、Windows 会话、可执行文件路径和受支持的版本，并在操作期间保留原生进程句柄，避免 PID 复用导致目标变化。仅限当前用户访问的所有权管道使各 CLI 进程的启动、关闭和重启操作依次执行，无需依赖线程绑定的互斥锁。桥接和守护进程协议均无需更改。

显式启动仅传入 `-noattach`。关闭使用 `Process.CloseMainWindow` 并等待退出，等待可取消。原生对话框由用户处理。重启先验证可执行文件，待进程退出后才从同一路径启动。两者均不保存捕获记录或停止守护进程。超时或取消只结束等待，不会终止 Fiddler 或启动替代进程。完整的命令与错误约定见 [CLI 指南](cli.md#fiddler-应用程序)。

## AutoResponder 模型

桥接在 UI 线程中访问 Fiddler 当前的 `AutoResponder` 实例。它为已加载的规则对象分配不透明 ID，公开原始匹配/操作文本，并通过 Fiddler 的原生提升/降低操作调整优先级。导入使用 Fiddler 的 FARX 导入器，替换使用其规则加载器。FARX 字节保留在磁盘上，协议中仅以经过校验的绝对路径表示。

桥接将原生操作交给 Fiddler 解释，保留其原生行为，无需第二套规则引擎。修改工具因此属于开放世界操作：操作可能影响网络流量，或使用当前用户权限读取本地响应文件。

## 断点模型

触发器是有容量限制的内存过滤器，用于匹配后续请求头或响应头。匹配时，扩展会设置 Fiddler 的 `x-breakrequest` 或 `x-breakresponse` 会话标记，并跟踪会话进入手动篡改状态的过程。一次性触发器会在匹配后立即移除。

待处理断点 ID 标识当前暂停。即使同一个 Fiddler 会话先在请求阶段暂停、再在响应阶段暂停，单调递增的序列号也可用作等待游标。托管暂停的保持时间为 1-300 秒，到期后桥接调用 `ThreadResume`。桥接也可发现和控制 Fiddler 中手动创建的暂停。这些暂停没有桥接设置的超时。

会话仍处于预期的手动篡改状态时，桥接才允许修改。请求暂停可修改方法、URL、请求头和正文。响应暂停可修改状态码、原因短语、响应头和正文。正文替换上限为 4 MiB。恢复或中止操作会先移除待处理句柄，再改变 Fiddler 状态，避免并发调用重复操作。

## 翻页

代理检查流量时，Fiddler 的抓包集合可能继续变化。`list_network_requests` 使用含边界值的请求 ID 范围分页，不使用页码。存在更多匹配过滤条件的结果时，响应会包含一个续传值：

- 按最新优先返回时提供 `nextMaxRequestId`。下次调用使用相同过滤条件，并将其作为 `maxRequestId`。
- 按最早优先返回时提供 `nextMinRequestId`。下次调用使用相同过滤条件，并将其作为 `minRequestId`。

请求 ID 范围可避免新增会话改变页码边界而产生重复结果。

## 输出边界

- 列表只包含元数据，不包含标头或正文。
- 详情仅在明确请求时包含保持原始顺序的标头，不包含正文。
- MCP 正文结果是带明确编码元数据的限长分块。
- WebSocket 列表只包含帧元数据。载荷使用独立的 64 KiB MCP 分块接口。
- CLI 正文输出保留完整原始载荷，不执行标准化。
- 大型归档使用绝对 `.saz` 路径表示，不以内联数据传输。
- FARX 规则集使用绝对 `.farx` 路径表示，不以内联数据传输。
- 断点详情包含元数据和可选标头。现有的限长正文工具用于读取暂停中的载荷。
- cURL、原始 HTTP、HAR 和 diff 都是显式的敏感证据操作。diff 返回正文哈希，不返回正文数据。

这些边界减少了常规调用的上下文消耗，同时保留抓包证据原貌。

## 元数据汇总与诊断

`sessions list --summary` 和 `summarize_network_requests` 共用 `SessionSummaryService`。该服务仅调用一次有数量上限的列表操作，拒绝标头和正文搜索，且只汇总返回记录。已捕获的请求和响应正文长度不包含标头或传输开销。已完成请求的有限耗时用于计算中位数和最近秩法 p95。匹配数、返回数和截断标记用于说明结果是否完整。数量上限仅限制输出，用于匹配过滤条件的元数据扫描不受此限制。

`DiagnosticExportService` 通过只读操作直接探测桥接和守护进程，不调用自动启动的中继，也不读取配置。独立的报告 DTO 仅允许数字版本、已知能力、监听状态和预定义错误，无法序列化流量、令牌字段、客户端名称、局域网地址、本地路径或原始异常。守护进程停止时，报告无法确定已保存的监听设置。服务以原子方式发布文件，不覆盖已有文件。输出路径回执与报告分开。

CLI 命令按诊断与生命周期、会话检查、会话操作、WebSocket、请求和 HTTP 管理组织，共用选项和输出辅助代码。分发器分部文件分别负责检查、修改、投影、完成等待和 WebSocket 访问，并保留 UI 线程入口。管理面板将布局与交互逻辑分开。

## 安全模型

工具注解区分只读检查、破坏性删除或传输中修改，以及开放世界网络操作。清空、选择性删除、归档/FARX 替换、规则删除和会话中止会在适用情况下要求明确确认。托管 HTTP 还要求确认远程启用、客户端撤销、连接断开，以及存在客户端连接时的服务禁用。已捕获的标头和正文不会被静默脱敏，调用方必须将显式输出的证据视为敏感数据。

主程序连接用户正在运行的 Fiddler Classic。它不会自动启动 Fiddler、在没有命令的情况下挂接系统代理，也不会安装或信任证书。将 MCP HTTP 绑定到 `0.0.0.0` 需要显式指定 IPv4 选项。该模式使用明文 HTTP，强制要求 Bearer 身份验证，不会启用 CORS，也不会自动配置 TLS、证书或防火墙。由于没有获准访问的浏览器来源，两种 HTTP 模式均对携带 Origin 的请求返回 HTTP 403。客户端提供的 MCP 元数据不能授予访问权限或确定已授权客户端的身份，身份由 Bearer 验证决定。

## 有意保留的差异

Chrome DevTools MCP 将 `list_network_requests` 和 `get_network_request` 的范围限定为单个页面。本项目使用同样以请求为中心的 MCP 术语，查询 Fiddler Classic 的进程级会话列表。独立的 `get_network_request_body` 工具可避免常规元数据调用意外返回大量或敏感载荷。面向用户的 CLI 使用 `sessions`，与 Fiddler Classic UI 的术语一致。
